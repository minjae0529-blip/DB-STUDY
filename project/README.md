## 수업 준비

이 폴더의 **`setup.sql`**을 root로 실행하세요. 프로젝트 DB **`hanip_delivery13`**이 만들어집니다. 한입배달 기본 데이터 + 쿠폰 테이블(Ch08)에서 시작합니다.

SHOW DATABASES LIKE 'hanip_delivery%';   -- 01 ~ 12, 그리고 13

## 오늘의 요청

> **From.** 데이터팀 김 팀장 · 마케팅팀 이 매니저
>
> 다음 분기 핵심 과제는 **단골 고객 유지**입니다. 한입배달에 **"단골 리워드"** 포인트 제도를 붙여 주세요.
>
> - 배달이 완료되면 결제 금액의 일정 비율을 **포인트로 적립**합니다. 비율은 **등급마다 다릅니다**(일반 1% · 실버 2% · 골드 3% · VIP 5%). 정책은 바뀔 수 있어요.
> - 다음 주문 때 포인트를 **현금처럼 사용**할 수 있습니다. 잔액보다 많이 쓸 수는 없습니다.
> - 적립한 포인트는 **6개월 뒤 소멸**합니다. 소멸 한 달 전에 알림을 보내야 해요.
> - 고객센터는 고객의 **포인트 내역과 잔액**을 조회할 수 있어야 하지만, **바꿀 수는 없어야** 합니다.
> - 마케팅팀은 등급별 적립 현황, 소멸 예정 고객, 포인트를 한 번도 받지 못한 고객 같은 **분석 리포트**가 필요합니다.
>
> 요구사항 정리부터 ERD, 테이블, 데이터, 분석 쿼리, 뷰·인덱스·권한까지 전부 부탁합니다.

## 분석 쿼리 10개

각 쿼리 위에 **누가 왜 묻는 질문인지** 주석으로 쓰세요. 결과 행 수도 적습니다.

| # | 질문 | 쓰게 될 기술 |
|---|---|---|
| 1 | 포인트 잔액 상위 10명 (이름, 등급, 잔액) | 집계, 정렬 |
| 2 | 월별 적립 포인트 합계와 적립 건수 | `DATE_FORMAT`, GROUP BY |
| 3 | 다음 달 소멸 예정 포인트가 있는 고객과 금액 (알림 대상) | 날짜 범위 조건 |
| 4 | 등급별 고객 수와 평균 잔액 | 뷰 위에 집계 |
| 5 | 포인트를 한 번도 적립받지 못한 고객 | LEFT JOIN / NOT EXISTS |
| 6 | 가게별 "포인트 사용 주문" 비율 | CASE, 비율 계산 |
| 7 | 고객별 적립 포인트 순위 (등급 안에서) | 윈도우 함수 `RANK() OVER (PARTITION BY …)` |
| 8 | 적립액이 평균보다 많은 고객 | 서브쿼리 |
| 9 | 등급 정책을 바꾸면(예: 골드 3% → 4%) 6월 적립액이 얼마나 늘어나는지 | 시뮬레이션 계산 |
| 10 | 자유 주제 — 마케팅팀에 제안할 인사이트 하나 | 팀 선택 |

## 설계할 때 꼭 따져 볼 질문

1. **잔액을 저장할까, 계산할까?** 고객 테이블에 `point_balance` 열을 두면 조회는 빠르지만 내역과 어긋날 위험이 있습니다(Ch09 6절). 어떤 선택이든 **근거**를 발표하세요.
2. **적립률이 바뀌면 과거 적립은?** 정책 테이블만 참조하면 과거 내역이 바뀐 것처럼 보입니다. `unit_price`를 왜 저장했는지 떠올리세요(Ch09).
3. **한 주문에 두 번 적립되면?** DB가 막을 수 있나요? (UNIQUE)
4. **잔액보다 많이 쓰면?** CHECK로는 다른 행의 합계를 검사할 수 없습니다. 트랜잭션에서 어떻게 막나요? (Ch08)
5. **소멸은 어떻게 기록하나?** 행을 지우나요, 마이너스 내역을 남기나요? 회계 감사를 생각해 보세요.
6. **고객센터 계정**은 어떤 테이블·뷰를 볼 수 있어야 하나요? 전화번호는?
7. **적립은 트리거로, 사용은 프로시저로?** 배달완료는 앱·관리자·배치 등 어디서든 일어나므로 트리거가 어울리고, 포인트 사용은 검증과 트랜잭션이 필요한 **작업**이라 프로시저가 어울립니다. 반대로 설계했다면 그 이유를 발표하세요(Ch11 8절).
8. **취소된 주문의 적립은?** 배달완료 후 취소(환불)되면 적립을 되돌려야 하나요? 마이너스 내역으로 남길까요?

## 제출 형식

GitHub 저장소 하나에 아래 구조로 올립니다.

```
reward-project/
├── README.md          요구사항 · ERD(mermaid 또는 이미지) · 설계 결정과 근거
├── 01_ddl.sql         CREATE TABLE · 제약조건
├── 02_data.sql        정책 · 적립 · 사용 · 소멸 데이터
├── 03_automation.sql 적립 트리거 + 포인트 사용 프로시저 (성공 / 잔액 부족 실패 두 경우)
├── 04_queries.sql     분석 쿼리 10개 (각 쿼리 위에 질문 주석 + 결과 행 수)
├── 05_ops.sql         뷰 · 인덱스(EXPLAIN 전후) · 계정 · 역할
└── slides.pdf         발표 자료
```

모든 SQL 파일은 `setup.sql` 직후 **위에서부터 순서대로 실행했을 때 에러 없이** 돌아가야 합니다. 제출 전에 `setup.sql`의 DROP 줄 주석을 풀고 처음부터 다시 실행해 확인하세요.
