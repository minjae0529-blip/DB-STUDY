## 강조할 것

1. **"JOIN 결과 행 수는 몇 개여야 하나?"를 매번 묻는다.** 쿼리를 실행하기 전에 예상 행 수를 말하게 하세요. 1:1이면 그대로, 1:N이면 늘고, INNER면 줄 수 있고, ON을 빠뜨리면 폭발합니다.
2. **필수 관계는 INNER, 선택 관계는 LEFT.** 주문–고객은 필수, 주문–기사는 선택(`rider_id` NULL 허용). `DESC orders`의 `Null` 열로 판단하는 법을 보여 주세요.
3. **ON vs WHERE**는 시험·면접·실무 버그 모두 단골입니다. 규칙 두 줄(오른쪽 거르기는 ON, 왼쪽·최종 거르기는 WHERE)을 외우게 하세요.
4. **fan-out은 에러가 나지 않는다.** 유일한 방어는 다른 숫자와 대조하는 것. 9절에서 Ch04 리포트의 건수와 맞춰 보는 장면을 꼭 보여 주세요.

## 자주 나오는 질문

| 질문 | 답변 요지 |
|---|---|
| "`JOIN`이랑 `INNER JOIN` 달라요?" | 같음. `INNER`는 생략 가능 |
| "`LEFT OUTER JOIN`은요?" | `LEFT JOIN`과 같음 |
| "`FROM a, b WHERE a.x = b.x`도 되던데요?" | 옛날 문법(암시적 조인). 조건을 빠뜨리면 CROSS JOIN이 되어 위험. ON으로 통일 |
| "JOIN 순서가 성능에 영향 있어요?" | INNER JOIN은 옵티마이저가 순서를 정함. LEFT는 의미가 달라지므로 순서 중요 |
| "USING이 더 짧은데 왜 ON을 써요?" | 회사 DB는 키 이름이 다른 경우가 많음. 조건이 눈에 보이는 ON이 안전 |

## 자주 하는 실수

| 실수 | 증상 | 대처 |
|---|---|---|
| 별칭 없이 겹치는 열 | 1052 ambiguous | 모든 열에 별칭 |
| 별칭 붙인 뒤 원래 이름으로 참조 | 1054 Unknown column 'orders.x' | 별칭으로만 |
| ON 조건 누락 / 잘못된 키 연결 | 행 수 폭발, 엉뚱한 짝 | 예상 행 수 먼저 말하기 |
| LEFT JOIN 후 오른쪽 조건을 WHERE에 | 0건 행 사라짐 | ON으로 이동 |

| 주문 상세 JOIN 후 `COUNT(*)`를 주문 수로 | 줄 수가 나옴 | `COUNT(DISTINCT o.order_id)` |
